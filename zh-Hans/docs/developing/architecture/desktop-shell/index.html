The desktop app is a window over the local Python backend. The shell starts or attaches to the backend, serves the React frontend, and supplies what a browser cannot: a tray icon, native notifications, global shortcuts, file dialogs and embedded web pages.

Suzent is moving its shell from Tauri (src-tauri/) to Electron (apps/desktop/) so every platform renders with the same Chromium engine; see the roadmap for the remaining steps. Until the switch, both shells build from the same frontend.

Talking to the shell

The frontend never imports a shell API directly. frontend/src/lib/desktop.ts is the only bridge: invoke(command, args), listen(event, callback), window controls, openUrl, openDialog, global shortcuts and notification permission. Under Electron it calls window.suzentDesktop, which the sandboxed preload (apps/desktop/src/preload.ts) exposes; under Tauri it calls @tauri-apps/*. Both shells answer the same command names (get_backend_port, frontend_ready, get_service_status, resolve_close and so on), so a component works in either. Gate every call on isDesktop(): the same bundle also runs as the web UI.

Window dragging differs: Tauri needs a startDragging() call on mouse down, while Electron drags through CSS. Mark draggable areas with data-tauri-drag-region (the element itself) or data-window-drag (an area with controls inside); styles.css turns both into app-region: drag under Electron and keeps buttons, links, inputs and anything with [data-no-drag] clickable.

Runtime layouts

apps/desktop/src/layout.ts decides where the backend comes from:

  • Bundled (an installed app): <resources>/runtime/python is a relocatable CPython with Suzent installed, and <resources>/suzent holds the read-only config/, skills/, plugins/ and browser extension, passed to the backend as SUZENT_PROJECT_DIR. This is the layout the Microsoft Store package already uses.
  • Source (development): the checkout that contains apps/desktop, or SUZENT_DIR. The backend runs from the checkout's .venv, or uv run when there is none. suzent start in a development checkout runs this shell (apps/desktop/node_modules/electron on apps/desktop) on frontend/dist; suzent start --dev and npm run dev in apps/desktop run it on the Vite dev server through SUZENT_DEV_URL.

Writable state always lives in the data dir (~/.suzent, or SUZENT_DATA_DIR).

Backend lifecycle

On start the shell tries to attach to a healthy backend on SUZENT_PORT or the background service port (25314). It only attaches to one that belongs to this install: a bundled app accepts another bundled backend of the same version, a development run only one started from the same checkout. A different Suzent on that port is reported, never stopped. Otherwise it starts an owned child with SUZENT_RUN_MODE=desktop-child, waits for runtime/server.port, then for /health, and injects the port into the page. Quitting asks an owned backend to stop through /service/stop with a per-launch token, then kills it if it has not exited after 15 seconds.

The page is served from suzent://app, a privileged custom scheme, with the same Content Security Policy the Tauri build used. The backend's CORS policy and browser-extension setup trust that origin alongside the Tauri ones.

Closing and the tray

On Windows and macOS closing the window asks, hides to the tray, or quits, per the saved choice in ~/.suzent/desktop/close-action. Linux has no tray, so closing quits. Quit, Dock Quit, Cmd+Q and restarts all pass through before-quit, which marks the app as exiting so the close they cause is not turned into a hide. The tray polls /focal/chats every four seconds and shows chats waiting on the user and chats running; on Windows the icon gets a red dot when something waits.

The agent's browser

The Electron shell hosts the browser tool's pages (connection_mode desktop, the default). apps/desktop/src/agentBrowser.ts keeps one WebContentsView per agent tab in the persist:suzent-agent-browser partition, or the in-memory suzent-agent-browser partition when the desktop_persistent browser setting is off (the backend sends it in its ready message and as a configure request on change; switching closes every tab). The tabs are sandboxed, no preload, every permission request and download refused, navigation limited to http(s) and about:blank. Each tab's webContents.debugger carries DevTools commands, so no remote-debugging port is opened and the app's own page is never reachable.

agentBrowserLink.ts dials the backend's /ws/browser-desktop on loopback and authenticates with the token the backend writes at start to runtime/desktop-browser-<port>.token (mode 0600; Windows relies on the profile folder's ACL). The backend refuses connections that carry an Origin header, so web pages cannot use the socket. The protocol is the browser extension's (tabs, select, open, cdp, status, focus, detach), and src/suzent/tools/browser/extension/session.py's BridgeSession serves both; only an allow-list of Page, Runtime.evaluate and Input methods is relayed.

While the Browser panel is closed, the controlled page stays shown in a 1×1 pixel view with Emulation.setDeviceMetricsOverride at 1280×800: Chromium drops input to hidden pages and stops painting them. The panel (AgentBrowserPane.tsx) calls agent_browser_show with its bounds, which clears the override and lays the page over the panel.

The panel also draws a tab bar and an address bar. agent_browser_state and the agent-browser:state event give it the tabs (title, URL, loading, back/forward), and agent_browser_command carries the user's select/new/close/navigate/back/forward/reload/stop. Typed text goes through addressUrl(): a web address as is, a bare host over https (http for localhost), anything else to a Bing search. A tab the user picks, opens or closes there becomes the agent's tab too, sent to the backend as a selected event. agent_browser_clear_data closes the tabs and clears both partitions' storage and cache.

Without the app (web UI, headless service) effective_mode reports managed and the Playwright session runs instead; it prefers an installed Chrome or Edge and downloads Chromium only when neither exists.

Installers

apps/desktop/electron-builder.yml wraps the shell, the frontend build and the bundled runtime into standard installers:

PlatformInstallersInstalls to
WindowsSuzent-Setup-*.exe (drawn setup around a one-click, per-user NSIS package; no admin prompt)%LOCALAPPDATA%\Programs\Suzent, or a folder the user picks
macOS (Apple silicon).dmg and .zip, signed with the hardened runtime and notarized/Applications/SUZENT.app
LinuxAppImage and .deb/opt/SUZENT (deb)

scripts/build_desktop_runtime.py builds the runtime for the platform it runs on: it copies uv's python-build-standalone CPython 3.12 (never installing into uv's own copy), installs Suzent and its locked dependencies non-editable with the social, camera and wake extras the built-in plugins need, strips Tcl/Tk and test suites, precompiles bytecode (the install dir may be read-only) and checks that the result imports and does not point at a checkout. It also copies the tracked config/, skills/, plugins/ and extensions/browser/ into resources/suzent with a bundle.json.

bundle.json next to the runtime is how a backend started without the shell's environment (the background service, the suzent command) still knows it is bundled: bundled_resources_dir() in suzent/config/paths.py looks for it beside sys.prefix.

Windows users download Suzent-Setup-<version>-win-x64.exe. It is a small Tauri program (apps/desktop-setup) drawn like the app's onboarding wizard and startup screen, with the electron-builder NSIS package appended to it (apps/desktop/scripts/build-setup.mjs writes the trailer that src/payload.rs reads). It checks the chosen folder (writable, not Program Files), runs the package with /S /D=<folder>, shows progress from how much of the app has landed there, then checks that suzent --version runs. --silent [--dir PATH] does the same without a window. Updates skip it: electron-updater runs the NSIS package itself, which keeps the folder from the registry. The disk image background is drawn in installer/art/dmg-background.html and rendered by scripts/render-dmg-background.mjs.

The suzent command comes with the install. installer/bin/ holds a suzent.cmd and a suzent script that run python -m suzent.cli on the bundled runtime. The Windows installer adds resources\bin to the user's PATH (installer/installer.nsh) and removes it on uninstall; on macOS and Linux the app writes ~/.local/bin/suzent on launch (src/cliShim.ts), never over a suzent that it did not write, and not from an AppImage, whose mount point changes every run. suzent update, upgrade and repair refuse to run in a bundled install, which updates as a whole.

.github/workflows/desktop-installers.yml builds the installers on Windows, macOS (Apple silicon) and Linux, installs each one as a user would (the Windows setup with --silent, the app copied out of the dmg, apt install of the deb, the extracted AppImage), checks the suzent command, runs the smoke test against the installed app and, on Windows, uninstalls it again. Run it by hand with sign to sign and notarize the macOS builds with the release certificates.

Development

To build installers locally:

npm run e2e -- --app <packaged executable> runs the same smoke test against an installed build. CI runs the unit and smoke tests on Linux, Windows and macOS.
