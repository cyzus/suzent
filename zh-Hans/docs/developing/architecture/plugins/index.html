This page is for plugin authors and contributors. For installing and enabling plugins, see Plugins.

A plugin is a unit the user installs and removes. It can bring packages, code, or both:

  • Packages. A built-in plugin names extras from Suzent's own pyproject.toml: each chat app has its own extra and plugin (telegram, slack, discord, feishu), and the social extra still pulls in all four for scripted installs. A third-party plugin lists pip requirements instead.
  • Code. An __init__.py with register(ctx) adds tools, slash commands and skills.

For code, a plugin is the in-process counterpart to MCP: reach for MCP when a tool should work with any agent or needs process isolation, and for a plugin when it should use Suzent's own tool pipeline (approvals, output caps, ToolSearch), add slash commands, or ship skills.

Layout

plugin.yaml:

FieldMeaning
aliasesOther names suzent plugin install and the API accept, e.g. lark for feishu.
channelThe chat app this plugin provides, as keyed in config/social.json. See Chat-app plugins.
extrasExtras of Suzent's own package this plugin needs. Only meaningful for built-in plugins.
dependenciespip requirements of a third-party plugin.
default_enabledOn until the user removes it. Honoured only for built-in plugins.

PluginContext

MethodWhat it does
register_tool(tool_cls)Adds a suzent.tools.base.Tool subclass. It goes through the same _make_tool() wrapper as built-in tools, so requires_approval, output_char_limit, the user's approval policy and ToolSearch deferral all apply. Without a group it is not in the tool picker and is reached through ToolSearch; with one it is listed under that capability.
register_skills(path)Adds a directory of skill folders. Relative paths resolve against the plugin directory. Skills get source plugin and id plugin:<plugin-id>:<skill-name>, are enabled by default, and are mounted read-only into the sandbox under /mnt/skills/plugins/.
register_command(aliases, **options)Decorator with the same signature and handler contract as suzent.core.commands.base.register_command.
id, manifest, path, loggerThe plugin's id, parsed manifest, directory (None for pip packages) and a logger bound to suzent.plugins.<id>.

Registrations are buffered on the context and committed only after register() returns. If it raises, the plugin is marked error and nothing it registered reaches the live registries.

Name clashes never replace existing behaviour: a tool whose name or tool_name is already taken, or a command with an alias already registered, is skipped with a warning.

Discovery and loading

suzent.plugins.manager.PluginManager finds plugins in, from lowest to highest precedence:

  1. <repo>/plugins/<id>/, the built-in plugins shipped with Suzent.
  2. Packages exposing an entry point in the suzent.plugins group. The entry point's name is the plugin id; its target is register or a module defining it. Version and description come from the package metadata.
  3. <data dir>/plugins/<id>/.
  4. Each directory in SUZENT_PLUGINS_DIR (os.pathsep-separated).

A later source with the same id replaces an earlier one, so a checkout under SUZENT_PLUGINS_DIR overrides an installed copy.

Discovery reads only manifests and package metadata. The user's choices live in <data dir>/config/plugins.json:

A plugin with no entry is on only if it is built-in and either default_enabled or a chat-app plugin whose app is set up; an explicit false is kept, so a removed default stays removed. requested_by records the names the user installed it under.

A plugin's code is imported only when it is enabled. The initial load is lazy, the first time the tool registry, the skill manager or the slash-command registry is used. After that, activate() and deactivate() load and unload single plugins in the running process (see Hot loading). A plugin whose api_version is newer than the running Suzent supports is refused.

Dependencies

suzent.plugins.deps installs what a plugin needs. Installing never removes anything, so it is safe while the backend runs from the same environment.

  • Extras go into Suzent's environment with uv sync --frozen --inexact --extra <every enabled plugin's extras>, run in the project directory. --inexact adds missing packages and leaves the rest. A Suzent that was installed with pip rather than from a checkout has no uv.lock, so the install fails with the pip install 'suzent[...]' to run instead.
  • Third-party dependencies go into <data dir>/plugins/.deps/<id>/ with uv pip install --target (or pip when uv is missing), and that directory is added to sys.path when the plugin loads. Keeping them out of the environment means the exact uv sync an upgrade runs cannot remove them.

suzent upgrade builds its sync from the same state: _backend_sync_args() passes --extra for each extra an enabled plugin needs, plus dev in a development checkout. That sync is exact, so packages of plugins the user removed are cleaned up then. A checkout older than plugins (no plugins/ folder, for instance after a rollback) gets --extra social, as before. _plugin_extras() reads config/social.json from the checkout too, so a chat app that is set up but has no state entry keeps its packages.

missing_packages() compares what a plugin declares with what is installed, for suzent plugin status and the settings page.

Settings page and API

RouteWhat it does
GET /pluginsEvery plugin with enabled, status, missing packages and restartRequired.
POST /plugins/{name}/installEnables a plugin by id or alias, installs its packages, activate()s it, and, when it brought packages, rebuilds the social stack with reload_social() so a chat app whose SDK just arrived connects. A failed install returns 502 with uv's output; the plugin stays enabled so a retry reinstalls.
POST /plugins/{name}/removeDisables and deactivate()s a plugin, and for one that brought packages, rebuilds the social stack so its chat app stops.

suzent plugin install and remove call these routes when a server answers (suzent.client, PluginsAPI), so a change from the terminal applies to the running process too. With no server they write the state and install packages themselves, and the next start loads the result.

restartRequired is true only when the running process disagrees with the saved state, which now happens only after an out-of-band change such as a hand-edited plugins.json.

Chat-app plugins

plugins/telegram, slack, discord and feishu are packages-only plugins with a channel field. They have no default_enabled; instead a chat-app plugin with no state entry is on when its section of config/social.json is set up: enabled is not false and some value other than enabled and allowed_users is non-empty. This is evaluated on every discover(), so users who configured an app before the split keep its packages on upgrade without a migration step.

The plugin and the app's own switch are kept in step:

  • Saving Settings → Social Channels (save_social_config) enables the plugin of every app that is set up, installs missing packages in a worker thread, then calls reload_social().
  • set_enabled() on a chat-app plugin writes the same value to that app's enabled in social.json, if the app has a section there.

ChannelManager asks for_channel() and skips a configured app whose plugin is removed. Apps no plugin claims, such as WeChat, always load.

Hot loading

PluginManager.activate(id) runs a newly enabled plugin's register() (or retries one that failed), and deactivate(id) takes a disabled plugin's commands out of the slash-command registry, drops its deps directory from sys.path, and forgets its module so the next activate() runs current code. Both then refresh what depends on the plugin set:

  • the tool registry caches (reset_tool_caches()),
  • the skill manager singleton (SkillManager.reset_instance()),
  • the cached agent (agent_manager.invalidate_agent()), so the next message builds an agent with the new tool list.

Only modules the process already imported are touched, so the CLI never imports the agent stack. A run already in progress keeps the agent it started with. Objects a plugin created itself (threads, open connections) are not torn down; a plugin that starts any should stop them when its module is garbage collected or provide no such state.

Security model

Plugins run in the Suzent process with the user's permissions. Only built-in plugins can turn themselves on; any other plugin stays off until the user installs it, which is the consent step, and the settings page asks for confirmation before installing third-party code. There is no sandbox and no capability system around plugin code. The API only accepts names of discovered plugins, never package names. Tools a plugin adds are still subject to the user's tool approval policy, the same as built-in tools.
